# RAG 检索质量排查方案（最终版）

## 排查流程

```
Step 1: 失败案例分析（Top-50 查全量） → 定位根因类别（A/B/C）
    ↓
Step 2: 消融实验（组件开关对比）      → 量化每个组件的净贡献
    ↓
Step 3: 参数调优（针对性调参）        → 根据根因调具体参数
    ↓
Step 4: 生成评估（RAGAS）            → 验证端到端质量
```

---

## Step 1：失败案例分析——Top-50 查全量定位根因

**目标**：用 Top-50 检索覆盖全量候选集（5 份文档 × 2-3 chunk/份 ≤ 15 条），精确分类每个失败 case。

### 三类根因

| 类别 | 判定条件 | 根因 | 对应优化方向 |
|------|---------|------|-------------|
| A 类 | 答案在 Top-5 内，但关键词匹配没达标 | 评测匹配策略问题 | 调整匹配阈值（已做） |
| B 类 | 答案在 Top-6~50，但没进 Top-5 | 排序/Rerank 问题 | Step 2 消融 + Step 3 调参 |
| C 类 | 答案不在 Top-50 任何位置 | 嵌入/分块问题 | 调整 chunk_size 或嵌入模型 |
| ~~A'类~~ | ~~Top-5 中完全不相关文档~~ | ~~召回失败~~ | ~~归入 C 类~~ |

### 执行脚本

`tests/rag_debug_failures.py`（已写好，跑一次即输出 A/B/C 占比 + 每题的 Top-5 关键词命中详情）

### 预期判断

- 如果 **A 类为主** → 当前 81% 的剩余 19% 主要是匹配策略的边界 case，系统检索本身没问题
- 如果 **B 类为主** → Step 2 消融实验定位哪个排序组件有问题
- 如果 **C 类为主** → 嵌入/分块是瓶颈，需回到嵌入流程排查

---

## Step 2：消融实验——量化每个组件净贡献

**目标**：逐个开关检索组件，看 Hit Rate 变化，找出增益最大和拖后腿的组件。

### 当前检索流水线

```
查询重写 → 向量检索 + BM25 → RRF 融合 → MMR 多样化 → gte-rerank 重排序 → Top-5
```

相关配置项及当前值：

| 组件 | 配置项 | 当前值 |
|------|--------|--------|
| 查询重写 | `QUERY_REWRITING_ENABLED` | `True` |
| 混合检索 | `HYBRID_SEARCH_ENABLED` | `True` |
| RRF 融合 | `RRF_CONSTANT_K` | `30` |
| MMR 多样化 | `MMR_ENABLED` / `MMR_LAMBDA` | `True` / `0.7` |
| 重排序 | `RE_RANKING_ENABLED` / threshold | `True` / `10` |
| 相似度阈值 | `SIMILARITY_THRESHOLD_BASE` | `0.15` |

### 消融实验表

| 实验 | 向量 | BM25 | RRF | MMR | Rerank | 查询重写 | 验证什么 |
|------|------|------|-----|-----|--------|---------|---------|
| 1. 纯向量 | ✓ | | | | | | 嵌入基线 |
| 2. +BM25 | ✓ | ✓ | ✓ | | | | BM25 贡献（RRF 需要两个源） |
| 3. +MMR | ✓ | ✓ | ✓ | ✓ | | | MMR 是否误杀 |
| 4. -Rerank | ✓ | ✓ | ✓ | ✓ | | ✓ | 接近完整链路但不 Rerank |
| 5. 完整链路 | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | 当前状态（基线对比） |

> 注意：RRF 融合需要至少两个检索源才有意义，所以不单独测 RRF。Rerank 在候选 > 10 时才触发（`RE_RANK_THRESHOLD=10`），当前 11 个 chunk 刚好踩线，预期 Rerank 收益极小。

### 执行方式

写一个消融脚本 `tests/rag_ablation.py`，通过 monkeypatch 修改 `settings` 的对应配置项，逐轮跑评测。每轮输出 Hit Rate@1/@3/@5 + MRR + 检索延迟。

### 预期判断

- 如果 **实验 4（-Rerank）≈ 实验 5（完整链路）** → Rerank 零收益，可以关掉省 2-3 秒
- 如果 **实验 2（+BM25）>> 实验 1（纯向量）** → 混合检索是关键，简历强调"BM25+向量混合检索"
- 如果 **实验 1（纯向量）已经接近 80%** → 你的场景候选集太小，复杂流水线反而增加延迟

## Step 3：参数调优——根据前两步结果针对性调参

**目标**：不盲目扫参，根据 Step 1 的失败分类和 Step 2 的组件贡献，只调有问题的环节。

### 如果 B 类多（排序问题）

| 参数 | 当前值 | 范围 | 说明 |
|------|--------|------|------|
| `MMR_LAMBDA` | 0.7 | 0.5~0.9 | 越高越注重相关性（而非多样性），小文档集建议调高 |
| `SIMILARITY_THRESHOLD_BASE` | 0.15 | 0.10~0.25 | 调高 = 更严格过滤，调低 = 更多候选进入重排 |
| `RRF_CONSTANT_K` | 30 | 10~60 | 越小越强调排名靠前的结果 |

### 如果 C 类多（召回问题）

| 参数 | 当前值 | 范围 | 说明 |
|------|--------|------|------|
| `KNOWLEDGE_CHUNK_SIZE` | 800 | 400~1200 | 越小 = 更多 chunk = 更细粒度，但可能拆散语义 |
| `KNOWLEDGE_OVERLAP` | 150 | 80~200 | 增大可缓解语义截断 |
| `VECTOR_CANDIDATE_MULTIPLIER` | 3 | 2~5 | 调大 = 向量检索拿更多候选给 RRF |

### 特殊建议：Rerank Top-K

当前 `RE_RANK_THRESHOLD=10`，全量候选 11 条刚好触发。如果 Step 2 证实 Rerank 无贡献，建议：
- 短期：`RE_RANK_ENABLED=False` 直接关掉
- 长期：加条件判断 `if len(candidates) > 20` 才触发

---

## Step 4：生成评估——RAGAS 三指标

**目标**：验证检索 → 生成的端到端质量。

### 指标

| 指标 | 含义 | 目标值 |
|------|------|--------|
| Faithfulness | 生成答案是否忠实于召回上下文 | > 0.80 |
| Answer Relevancy | 生成答案与问题的相关性 | > 0.70 |
| Context Relevancy | 召回上下文与问题的相关性（Hit Rate 的"软版本"） | > 0.60 |

### 执行方式

在 `tests/rag_eval.py` 中增加 `search_with_rag()` 调用，对每条问题获取生成答案，用 RAGAS 的 `evaluate()` 函数计算三指标。如 ragas 库不可用，手动实现 Faithfulness（拆解答案陈述 → 逐一检查文档是否支撑）。

---

## 执行顺序

```
□ Step 1: 跑 failure_analysis.py → 输出 A/B/C 占比
□ Step 2: 跑 ablation.py         → 输出各组件贡献
□ Step 3: 根据 1+2 调参          → 再跑 eval 对比
□ Step 4: 跑 RAGAS 生成评估      → 输出端到端质量
```

每一步的结果决定下一步是否继续、往哪个方向走。

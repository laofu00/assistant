# 微服务架构设计

## 什么是微服务架构

微服务架构是一种将单一应用程序拆分为多个小型、独立部署服务的架构风格。每个服务运行在自己的进程中，通过轻量级通信机制（通常为 HTTP API）进行协作。

## 微服务设计原则

### 1. 单一职责
每个微服务只负责一个业务领域（Bounded Context），不应跨领域处理业务逻辑。

### 2. 服务自治
- 独立部署：每个服务可独立构建、测试、部署
- 独立数据库：每个服务拥有自己的数据库，避免共享数据库
- 独立技术栈：不同服务可使用不同的技术栈

### 3. 去中心化
- 去中心化数据管理
- 去中心化治理（不同服务可独立选择技术方案）

### 4. 容错设计
- 断路器模式（Circuit Breaker）：如 Sentinel、Hystrix
- 重试机制：指数退避 + 最大重试次数
- 降级策略：核心功能降级，非核心功能关闭
- 超时控制：防止级联故障

### 5. 可观测性
- 日志聚合：ELK（Elasticsearch + Logstash + Kibana）或 Loki
- 分布式追踪：SkyWalking、Jaeger、Zipkin
- 指标监控：Prometheus + Grafana
- 健康检查：/health 端点 + 就绪探针

## 通信模式

### 同步通信
- **REST API**：最常见的微服务通信方式
- **gRPC**：高性能二进制协议，适合内部服务通信
- **GraphQL**：灵活的查询语言

### 异步通信
- **消息队列**：RabbitMQ、Kafka、RocketMQ
- **事件驱动**：发布/订阅模式，服务间松耦合

### 事件溯源（Event Sourcing）
将状态变更作为事件序列存储，而非直接存储当前状态。优点：完整审计、时间旅行、CQRS 配合。

## 服务发现与配置

### 服务注册发现
- **Nacos**（阿里开源）：同时支持服务发现和配置管理
- **Consul**：HashiCorp 出品
- **Eureka**：Netflix 出品（已停止维护）

### 配置中心
- 动态配置刷新
- 环境隔离（dev/test/prod）
- 加密敏感配置

## API 网关

网关是微服务架构的统一入口，负责：
- **认证授权**：JWT 验证、权限校验
- **请求路由**：根据路径转发到对应服务
- **限流**：令牌桶/漏桶算法
- **负载均衡**：轮询/加权/一致性哈希
- **日志聚合**：统一请求日志
- **请求/响应转换**：协议转换、数据聚合

## 数据一致性

### 分布式事务
- **Saga 模式**：使用补偿事务实现最终一致性
- **TCC（Try-Confirm-Cancel）**：两阶段提交的变体
- **本地消息表**：通过数据库保证消息的可靠投递

### CAP 定理
在分布式系统中，一致性（Consistency）、可用性（Availability）和分区容错性（Partition Tolerance）三者不可同时满足。

## 容器化与编排

### Docker
- **Dockerfile**：定义应用镜像
- **Docker Compose**：本地多服务编排
- **多阶段构建**：减小镜像体积

### Kubernetes（K8s）
- **Pod**：最小部署单元
- **Service**：服务发现和负载均衡
- **Deployment**：声明式更新
- **ConfigMap / Secret**：配置管理
- **HPA**：水平自动扩缩容

## 监控与告警

### 黄金信号
- **延迟（Latency）**：请求响应时间
- **流量（Traffic）**：每秒请求数
- **错误率（Errors）**：失败请求比例
- **饱和度（Saturation）**：资源利用率

### 告警规则
- P0（紧急）：服务不可用，立即处理
- P1（重要）：功能降级，30分钟内处理
- P2（一般）：性能下降，2小时内处理
- P3（提示）：资源预警，下一工作日处理

## 微服务 vs 单体架构

| 维度 | 单体架构 | 微服务架构 |
|------|---------|----------|
| 部署 | 整体部署 | 独立部署 |
| 扩展 | 整体扩展 | 按需扩展 |
| 技术栈 | 统一 | 多样 |
| 复杂度 | 低 | 高 |
| 运维成本 | 低 | 高 |
| 团队规模 | 小团队 | 多团队 |

选择建议：小团队/快速迭代 → 模块化单体；多团队/独立扩展需要 → 微服务。
